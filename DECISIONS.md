# Decisions

Choices made where the spec was open, per rule 6 in the build prompt.

| # | Phase | Decision | Why |
|---|---|---|---|
| 1 | 0 | Only the customer app uses a route group (`(customer)`); partner, rider and admin are plain folders. | Keeps URLs exactly `/`, `/partner`, `/rider`, `/admin`, and gives each app its own layout. |
| 2 | 0 | Tailwind v4 (what Next 15 ships with) with shadcn/ui components written into `src/components/ui`. Theme tokens live in `globals.css`. | Current shadcn default; tokens give dark mode for free in Phase 10. |
| 3 | 0 | App icons are generated from brand colours by a route (`/icons/[size]`), not static PNGs. | Renaming or recolouring the brand needs no new image files. |
| 4 | 0 | Server layouts pass an app key (`"customer"`, `"rider"`…) to client nav components, which look up their items in `src/config/navigation.ts`. | Icon components can't be passed from Server to Client Components. |
| 5 | 0 | Every nav tab has a real page with an empty state from day one. | No dead links at any phase (checked by a Playwright test). |
| 6 | 0 | The Demo Switcher remembers the persona in `localStorage` and opens its app. Real sign-in as that persona arrives in Phase 2. | Auth doesn't exist until Phase 2. |
| 7 | 0 | Hindi strings will use a small typed dictionary, not an i18n library. | Two languages, demo scope. |
| 8 | 0 | Supabase can't run locally in the build sandbox (no Docker). Migrations and RLS are tested against plain Postgres 16 with a minimal `auth` schema stub; the app itself targets a hosted Supabase project. | Lets Phase 1 checks run without Docker. |
| 9 | 0 | Fonts: Inter (body) and Plus Jakarta Sans (headings) via `next/font`. | Warm, readable, self-hosted at build time. |
| 10 | 1 | Order status adds `PENDING_PAYMENT` (before Razorpay confirms) and `CANCELLED` (admin cancel) to the spec's state list. | An order row must exist before online payment; admin cancellations need a status distinct from customer ones. |
| 11 | 1 | A rider can be assigned while food is still being prepared (`rider_id` + `rider_assigned_at`). Status moves `READY → RIDER_ASSIGNED` as soon as both are true. | Matches how real riders are dispatched early, while keeping the spec's single status sequence. |
| 12 | 1 | Order status, money and wallet changes are written only by server code using the service role. RLS gives clients read access; there are no client UPDATE policies on orders or wallets. | "Never trust client totals" enforced at the database. |
| 13 | 1 | Sensitive onboarding fields (bank, PAN, GST, documents) live in `restaurant_private` / `rider_private`, readable only by the owner team / rider and admins. | Public restaurant and rider cards can be readable without leaking bank details. |
| 14 | 1 | Distance uses a Haversine SQL function with a lat/lng index and bounding-box prefilter instead of PostGIS. | Spec allows either; no extension dependency. |
| 15 | 1 | Delivery radius is 15 km (configurable in admin). | Lets the demo customer in Koregaon Park see most of the 40 seeded restaurants. |
| 16 | 1 | Solo carts live in the browser (Zustand, persisted); `carts`/`cart_items` tables are used for group orders. The server recomputes every price at checkout. | Instant cart UI; only group orders need shared state. |
| 17 | 1 | Seed data is generated by `scripts/seed/generate.ts` into `supabase/seed.sql` (deterministic IDs). `pnpm seed` applies it to `SUPABASE_DB_URL` and can be re-run. | Seed stays reviewable SQL, but realistic volume is generated, not hand-typed. |
| 18 | 1 | Unsplash photo IDs couldn't be checked from the build sandbox (network blocks it). Every image has a gradient + emoji fallback. | No broken images even if an ID is wrong. |
| 19 | 1 | `scripts/dev-stack` runs Postgres + Supabase Auth + PostgREST + a small gateway (storage and realtime stand-ins) for local testing without Docker. Production uses a real Supabase project. | Lets every phase be tested end to end in the sandbox. |
| 20 | 3 | Veg Mode shows only pure-veg restaurants and hides non-veg dishes and add-ons everywhere (home, search, menus, customisation). | Matches how Zomato's Veg Mode behaves. |
| 21 | 3 | "What's on your mind?" circles filter the home list by cuisine (`/?cuisines=…`) instead of opening search. | Results appear in place, and the filter can be shared as a URL. |
| 22 | 3 | Healthy Score uses stored nutrition when present, otherwise a deterministic estimate from the dish name and tags (marked with *). | Every dish gets a score in Healthy Mode without needing AI. |
| 23 | 3 | Review summaries use GPT-4o-mini when `OPENAI_API_KEY` is set (cached 6 h); otherwise a rule-based summary from ratings, tags and dish mentions. | Nothing breaks without a key. |
| 24 | 3 | Popularity stats (trending restaurants, trending searches) come from `security definer` SQL functions that return only aggregates. | Customers see popularity without access to other people's orders or searches. |
| 25 | 3 | Restaurants that are closed can still be browsed and added to the cart; checkout requires scheduling for later. | Lets people plan ahead, as the spec's "schedule order" implies. |
| 26 | 4 | Without Razorpay keys, checkout uses a labelled demo payment sheet (UPI/card/netbanking/wallets, with "Simulate failure"). With keys it uses Razorpay test checkout: order created server-side, signature verified server-side, webhook for `payment.captured`/`payment.failed`. | Works for the pitch without keys; switches to Razorpay as soon as keys are added. |
| 27 | 4 | One payments module serves every paid flow (orders, Gold, events, dining bills, wallet top-ups, healthy plans, ad budgets); handlers are idempotent. | Webhook and browser can both report a payment safely. |
| 28 | 4 | Wallet share of a split payment is deducted only after the online part succeeds. | No money held if the card/UPI step fails. |
| 29 | 4 | WELCOME50 is a welcome offer usable 3 times (not first-order-only) so the demo customer, who has history, can use it in the scripted demo. FIRSTBITE carries the first-order-only rule. `pnpm seed` resets coupon usage. | The 2-minute demo script applies WELCOME50. |
| 30 | 4 | Gold members get free delivery at Gold partners above ₹199 and an extra 10% (max ₹75) off, shown inside "Discount" and tracked in `gold_savings_paise`. | Spec lists both benefits. |
| 31 | 4 | Scheduled orders become PLACED 45 minutes before the slot via `/api/cron/scheduled-orders` (Vercel Cron, every 5 minutes). | Supabase pg_cron isn't available everywhere; Vercel Cron ships with the app. |
| 32 | 4 | Playwright runs with one worker. | Tests share seeded demo accounts and one database. |
| 33 | 5 | Accepting an order records ACCEPTED (with prep time) and moves straight to PREPARING; the kitchen sees a countdown. The restaurant or rider can mark "handed over" (→ PICKED_UP). | Matches the partner flow in the spec (New → Accept → Preparing → Ready → Handed over). |
| 34 | 5 | The order alert is a WebAudio chime that repeats every 2.5 s while any order is waiting, plus a browser notification. Browsers need one click ("Turn on order alerts") before playing sound. | No audio file to host; satisfies autoplay rules. |
| 35 | 5 | Realtime subscriptions load the session and call `realtime.setAuth` before joining, and fall back to polling (10–15 s) when the channel isn't connected. | Without the token, Realtime joins as anonymous and RLS hides the rows. Polling keeps the board correct if WebSockets are blocked. |
| 36 | 5 | With no outlet chosen, the partner console opens the outlet with the most recent order. | Multi-outlet owners land where the action is. |
| 37 | 6 | Rider dispatch: on acceptance, the order is offered to the nearest free, online human rider within 5 km (30 s to accept). In demo mode, if no human has accepted 15 s after acceptance, the nearest simulated rider takes it. | Spec's assignment and simulated-rider rules. |
| 38 | 6 | The simulated rider is advanced by "ticks": open tracking screens call `/api/sim/tick` every 2 s and Vercel Cron calls `/api/cron/dispatch` every minute. Each tick computes the rider's position from timestamps (20 s to the restaurant, 30 s to the customer), so it's safe to call from many tabs. | Serverless hosts can't run long-lived timers. Demo speed fits the 90-second walkthrough. |
| 39 | 6 | Riders confirm pickup by typing the last 4 digits of the order number, and finish by entering the customer's 4-digit delivery OTP. COD orders also require ticking "cash collected", which adds to the rider's floating cash. | Spec's pickup and OTP rules. |
| 40 | 6 | The tracking screen refreshes on realtime events and also whenever its 2-second tick reports a newer `updated_at`. | A missed realtime event can't leave the customer looking at a stale status. |
| 41 | 6 | The "rider assigned" entry in the order's activity log keeps the current status (from = to) with a note, instead of a separate status. | Riders can be assigned while food is still being prepared (see #11). |
| 42 | 7 | Browser "push" uses the service worker's `showNotification` when a realtime notification arrives and the tab is in the background, instead of Web Push with VAPID keys. | No extra keys or push service to configure; works across all four apps. |
| 43 | 7 | In demo mode, simulated riders and restaurants send a canned reply when the customer chats. | A solo presenter can show two-way chat. |
| 44 | 7 | The PDF invoice uses pdf-lib's built-in fonts and prints amounts as "Rs." | Standard PDF fonts can't draw ₹; avoids shipping a font file. |
| 45 | 7 | Reorder rebuilds the cart from today's menu (current prices, skipping unavailable items) using saved variant/add-on ids, falling back to names for older orders. | Prices and stock change; the server reprices at checkout anyway. |
| 46 | 7 | Placing an order fails (and the half-created order is removed) if its line items can't be saved. | Never leave an order without items. |
| 47 | 8 | Partner reports and payout statements are computed by SQL functions (`partner_report`, `payout_statement`) using India time for days and hours. | One definition for the partner console, admin console, weekly cron and CSV exports. |
| 48 | 8 | Restaurant payout = order value (item total + packaging − the restaurant's own offer discounts, delivered orders) − commission − 18% GST on commission + Food Rescue sales + adjustments. Platform coupons and Gold discounts are funded by Thaali. | Matches the spec's payout formula; restaurants aren't charged for platform promotions. |
| 49 | 8 | Weekly statements are regenerated, not duplicated: one per restaurant per week; unpaid statements refresh and keep admin adjustments; paid ones never change. | Safe to re-run the cron or the admin button. |
| 50 | 8 | Ad campaign metrics are simulated by "ticking" campaigns on page load and status changes: spend grows at the daily budget within the campaign dates; impressions, clicks and orders follow fixed per-campaign rates. Active campaigns set `restaurants.sponsored_until`. | Believable, deterministic numbers without a background job; discovery's Promoted badge works unchanged. |
| 51 | 8 | Restaurant offer codes are uppercase alphanumerics and can't reuse a platform coupon code. | Checkout matches platform coupons first, so a clashing code would never apply. |
| 52 | 8 | Low-stock alerts are a database trigger on `menu_items`, firing once each time stock drops to or below the threshold; stock and coupon counters are updated atomically in SQL. | Orders, inventory edits and the item editor all alert the same way; no lost updates under concurrent orders. |
| 53 | 8 | Saving a menu item updates variants and add-ons in place by id and deletes only removed ones. | Customers' open carts reference those ids. |
| 54 | 8 | Outlet roles: the owner can do everything incl. staff; a manager edits settings, hours and tables; an order taker handles orders and bookings and the online/busy/auto-accept switches, and sees the rest read-only. | Staff management stays owner-only (as RLS requires); order takers need quick status switches during service. |
| 55 | 8 | Staff invites activate when the invited email signs in (DB trigger on profile creation), or immediately if the account exists. Removing someone's last outlet makes them a customer again. | No invite tokens to manage; role changes stay server-side. |
| 56 | 8 | Onboarding documents (FSSAI, GST, cancelled cheque) and rider documents are stored in private buckets as object paths; admins view them through 10-minute signed URLs. Cover photos and logos stay public. | Legal and bank documents must not be publicly reachable. |
| 57 | 8 | Funnel events: `menu_view` on restaurant open, `add_to_cart` when a cart starts at a restaurant, `checkout_start` on every order attempt, `order_placed` when payment is secured. | Feeds the partner conversion funnel. |
| 58 | 9 | Every admin mutation goes through `adminAction()` (role check, audit-log entry, revalidation) and then uses the service-role client. | One place for authorisation and a complete audit trail. |
| 59 | 9 | "Run full demo" places a real COD order for the demo customer at Saffron Courtyard through the normal pricing and finalisation code, ignoring only opening-hours checks, then auto-accepts and lets the simulated rider deliver it (~90 s). A server loop advances it, and the polling screens (`/api/admin/demo/tick`, `/api/sim/tick`) carry it on if that loop is cut short. | A presenter can run it at any hour; every other check still applies; idempotent compare-and-set steps. |
| 60 | 9 | Refunds happen at most once per order: every refund path first claims the order (`refunded_at` null → now) before moving money. Razorpay refunds are simulated in demo mode and recorded on the timeline. | No double refunds across admin, rejection and customer-cancel paths. |
| 61 | 9 | Reject/suspend/block reasons are kept in the audit log and in the notification sent to the person, not in new columns. | Admin detail pages read the latest reason from the audit log; no schema churn. |
| 62 | 9 | Rider payout = earnings in the IST week (trips, tips, incentives) − COD cash held not already counted ± adjustments; marking paid records a cash deposit. A negative net shows as "Owed to Thaali". | Cash is deducted exactly once, following the app's own cash records. |
| 63 | 9 | Paid payout statements are locked by a database trigger; adjustments have their own log table and survive regeneration. | The service role bypasses RLS, so a policy alone can't protect paid statements. |
| 64 | 9 | Deleting a used coupon deactivates it instead. Platform coupons support percent, flat and free delivery; BOGO/free-item are restaurant offers. | Orders and redemptions reference coupons; platform coupons have no item columns. |
| 65 | 9 | Banner links are built from a typed target (restaurant, collection, coupon → `/cart?coupon=CODE`, or URL) and validated on save; banners honour their start/end dates. | No dead links from the home carousel. |
| 66 | 9 | Gold benefits and surge/fees are the same `platform_settings` keys the checkout bill engine reads. | What admins configure is exactly what checkout applies. |
| 67 | 9 | No app-wide `loading.tsx`. Loading states use `<Suspense>` inside individual pages instead. | With a root `loading.tsx`, Next.js 15.5 production builds intermittently left client navigations (search-param changes, list → detail links) suspended forever on the loading boundary. Removing it fixed the hangs (1/6 → 6/6 in a repro). |
| 68 | 10 | In demo mode there is no login wall: opening an app without a session (or with the wrong role) signs in that app's demo account via `/demo/enter` — `/` → customer (with a Koregaon Park location), `/partner` → Saffron Courtyard owner, `/rider` → Arjun, `/admin` → admin. The login page and Demo Switcher still work; RLS is unchanged. | The app is shown as a demo; viewers shouldn't need credentials. Each browser has one session, so use separate windows/profiles to watch several apps at once. |
